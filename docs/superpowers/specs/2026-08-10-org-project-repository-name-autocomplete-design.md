# 组织项目仓库名称自动补全设计

## 概述

组织项目详情页当前要求用户手工输入仓库 ID 后才能关联仓库。仓库 ID 适合作为内部稳定标识，但不适合作为用户需要查询和记忆的输入值。

本次改为按仓库名称自动补全：用户输入名称并从搜索结果中选择仓库，页面将对应仓库 ID 写入隐藏字段，现有后端继续按 ID 建立关系。这样既改善可用性，也保留仓库改名后关联关系不失效的特性。

## 目标

- 将用户可见的“仓库 ID”数字输入改为仓库名称搜索。
- 复用 Gitea 现有仓库搜索接口和自动补全交互。
- 搜索范围限定为项目所属组织中当前用户有权读取代码的仓库。
- 用户选择名称后仍向现有表单提交稳定的 `repository_id`。
- 防止手工输入的名称与隐藏仓库 ID 不一致。
- 不再向用户暴露查找仓库 ID 的操作负担。

## 非目标

- 不修改项目与仓库关系的数据模型。
- 不把仓库名称保存为关联关系的主键。
- 不修改关联仓库、主仓库的角色规则。
- 不改变后端对组织归属、代码读取权限、重复关联和主仓库唯一性的校验。
- 不新增专用于组织项目的仓库搜索 API。
- 不允许通过自由文本名称绕过搜索结果直接提交。

## 方案选择

采用“扩展现有自动补全能力并提交隐藏 ID”的方案。

现有 `/repo/search` 接口已经支持按 `uid` 限定仓库所有者，按当前登录用户裁剪可见仓库，并在结果中返回仓库 ID 和完整名称。现有 `attachSearchBox` 负责防抖请求、结果展示、鼠标选择和键盘操作，但当前只会把结果标题写回可见输入框。

本次小幅扩展该公共自动补全边界，使搜索结果能够携带提交值，并允许调用方在选择结果时同步隐藏字段。组织项目页面在此能力之上增加仓库关联所需的有效选择校验和已关联仓库过滤，不重复实现搜索下拉、键盘导航或请求取消逻辑。

未采用以下方案：

- 独立开发组织项目仓库搜索组件：会重复现有自动补全逻辑。
- 服务端一次加载全部仓库作为下拉选项：仓库数量增加后加载和查找体验较差。

## 用户界面

关联仓库表单保持现有横向结构：仓库、角色和提交按钮。

仓库控件调整如下：

- 标签由“仓库 ID”改为“仓库”。
- 可见输入框使用提示文本“输入仓库名称搜索”。
- 输入至少两个字符后发起自动补全搜索。
- 搜索结果显示完整仓库名称，例如 `org3/repo3`。
- 用户可使用鼠标或键盘选择结果。
- 角色选择继续提供“相关仓库”和“主仓库”。
- 页面视觉、控件高度和响应式布局沿用现有组织项目表单样式。

已关联仓库不出现在候选结果中。若过滤后没有候选项，沿用现有搜索组件的无结果行为，不额外增加空状态面板。

## 数据流

1. 服务端渲染关联表单时提供组织 ID、当前已关联仓库 ID 列表和现有项目版本。
2. 用户在可见输入框中输入仓库名称。
3. 自动补全请求 `/repo/search?q={query}&uid={organizationID}`。
4. 搜索接口只返回当前用户可见的该组织仓库。
5. 页面从结果中排除已经关联到当前项目的仓库。
6. 用户选择结果后，可见输入框写入完整仓库名称，隐藏的 `repository_id` 写入结果中的仓库 ID。
7. 表单继续向现有关联路由提交 `repository_id`、`role` 和 `version`。
8. 后端继续通过稳定 ID 加载仓库，并执行现有权限、组织归属、重复关联、数量限制和角色规则校验。

后端保存协议和数据库结构不变。仓库之后改名时，项目关联仍由仓库 ID 保持有效，页面展示继续从当前仓库记录读取最新名称。

## 选择状态与校验

可见名称和隐藏 ID 必须被视为一个选择状态：

- 选择搜索结果时，同时设置完整名称和仓库 ID。
- 用户在选择后再次编辑、粘贴或清空可见输入内容时，立即清空隐藏仓库 ID。
- 只有再次从当前搜索结果中选择仓库，隐藏 ID 才会恢复。
- 提交时如果可见输入为空，沿用必填校验。
- 提交时如果存在自由文本但没有有效仓库 ID，阻止提交并提示“请从搜索结果中选择仓库”。
- 校验错误在用户完成有效选择后清除。

客户端校验用于提供即时反馈，不能替代现有服务端验证。构造请求直接提交无效、不可见、跨组织或重复仓库 ID 时，服务端仍拒绝操作。

## 公共自动补全边界

现有搜索结果结构增加可选的机器值，现有调用方不提供该值时保持原有行为。选择回调或等价的可选配置只在调用方显式启用时触发。

公共搜索组件继续负责：

- 防抖和取消过期请求。
- 结果渲染和转义。
- 鼠标选择。
- 上下方向键、回车和 Escape 操作。
- 失焦和点击外部时关闭结果。

组织项目初始化逻辑负责：

- 构造带组织 ID 的搜索地址。
- 将仓库搜索响应映射为完整名称、仓库 ID 和描述。
- 过滤已关联仓库 ID。
- 同步可见名称和隐藏 ID。
- 在输入变化时使旧选择失效。
- 执行“必须从结果中选择”的表单校验。

此边界避免为单一页面复制自动补全实现，也避免让通用组件了解组织项目业务规则。

## 权限与安全

- 搜索请求使用当前登录会话，不暴露当前用户无权读取的仓库。
- `uid` 固定为项目所属组织 ID，不允许页面搜索其他所有者的仓库。
- 前端过滤已关联仓库只改善交互；重复关联仍由服务层拒绝。
- 隐藏字段不是可信输入，后端继续根据仓库 ID 重新检查仓库存在性、组织归属和代码读取权限。
- 页面不通过候选数量、隐藏计数或错误详情泄露不可见仓库信息。

## 无障碍与降级

- 可见输入框保留关联标签、必填语义和浏览器自动完成关闭设置。
- 搜索结果沿用现有键盘导航和选择能力。
- 校验消息通过原生表单校验接口绑定到可见输入框，使焦点落在用户能够修正的控件上。
- JavaScript 未加载时，用户无法完成仓库选择；若绕过页面提交空或伪造的仓库 ID，现有后端校验仍会拒绝请求。
- 不移除服务端错误反馈，网络或并发导致的失败继续通过现有 flash 消息显示。

## 测试策略

### JavaScript 单元测试

覆盖：

- 输入达到最小字符数后，搜索请求包含组织 ID 和查询文本。
- 搜索结果使用完整仓库名称并携带仓库 ID。
- 选择结果后，可见输入框和隐藏 `repository_id` 同步更新。
- 选择后修改输入内容会清空隐藏 ID。
- 已关联仓库不会出现在候选结果中。
- 自由输入但未选择结果时阻止提交并显示明确提示。
- 有效选择后校验错误被清除并允许提交。
- 公共自动补全组件的现有无机器值调用方式保持不变。

### 端到端测试

覆盖：

- 在项目详情页展开“关联仓库”。
- 按名称搜索同组织内可见仓库。
- 从候选结果选择仓库并保留“相关仓库”角色。
- 提交后仓库以完整名称显示在项目详情中。
- 已关联仓库再次搜索时不显示为候选项。

后端关联服务不变，现有权限和冲突测试继续作为服务端安全保障。本次只有在模板数据准备需要新增逻辑时才增加聚焦的 Go 路由测试。

## 验收标准

- 用户无需知道或输入仓库 ID。
- 输入仓库名称后能够看到当前组织内有权访问的匹配仓库。
- 搜索结果显示完整仓库名称，并支持鼠标和键盘选择。
- 选中仓库后提交的仍是正确、稳定的仓库 ID。
- 修改已选名称后不会错误提交旧仓库 ID。
- 未从结果中选择仓库时不能提交自由文本。
- 已关联仓库不出现在候选结果中。
- 角色选择、权限规则、版本控制、审计记录和数据库结构保持不变。
- 相关单元测试、lint 和可执行的端到端测试通过。
