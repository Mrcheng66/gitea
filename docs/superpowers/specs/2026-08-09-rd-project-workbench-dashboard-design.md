# 研发项目工作台登录首页设计

日期：2026-08-09

状态：已确认，待书面审阅

范围：Gitea 登录首页、组织项目概览、项目详情与代码进展聚合

## 1. 背景与问题

当前登录首页以个人贡献热力图、通用活动流和仓库侧栏为主体。这个结构适合通用代码托管平台，但不适合研发部门内部的项目管理场景：

- 用户进入系统后无法直接看到部门有哪些项目、由谁负责以及推进到什么阶段。
- 项目资料、人员责任和代码活动分散在项目列表、详情侧栏和代码活动页中。
- 原始提交记录描述仓库操作，但不能直接回答项目取得了什么成果。
- 空贡献图、“无活动”和空仓库面板会占据首屏，却不能帮助用户推进项目。
- 当前项目总账以表格和风险指标为主，人员与代码进展仍然缺少项目上下文。

本设计将登录首页从通用代码动态页改为研发项目工作台。项目管理是核心，人员责任用于明确协作关系，代码活动只作为项目推进的客观证据。

## 2. 产品目标

用户进入首页后，应能在十秒内回答：

1. 当前有哪些项目？
2. 哪些项目需要关注？
3. 每个项目由谁负责、谁参与？
4. 当前问题和下一步行动是什么？
5. 最近取得了什么真实研发进展？

同时服务两类内部用户：

- 研发负责人查看团队全景、责任归属、关键节点和风险。
- 一线研发查看自己负责或参与的项目以及与自己相关的下一步。

## 3. 产品原则

- 项目管理优先于代码动态。信息权重依次为项目目标与阶段、风险与下一步、责任归属与关键节点、代码进展证据。
- 人工判断与自动证据分离。负责人维护项目判断，系统聚合研发事实，两者不能互相静默覆盖。
- 风险必须可行动。任何阻塞或延期都必须尽量同时展示原因、下一步、执行人和期限。
- 代码数量不等于项目进展。不得使用提交数量或个人活跃度进行人员排名或绩效评价。
- 异常项目展开，正常项目压缩。首页信息密度根据管理价值变化，而不是让所有项目占用相同高度。
- 保留 Gitea 原生导航、权限、组织上下文和仓库入口，不建设独立应用壳。

## 4. 导航与上下文

### 4.1 登录首页

登录后的默认仪表盘继续使用现有 dashboard 路由，但主体改为研发项目工作台：

- 移除登录首页的贡献热力图。
- 移除登录首页的通用活动流和“无活动”占位。
- 移除登录首页右侧仓库列表面板。
- 贡献热力图仍可保留在用户个人资料页。
- 仓库、合并请求、Issue、里程碑和代码动态仍通过现有原生入口访问。
- 增加“全部代码活动”次级入口；该入口在当前 dashboard 路由追加 `view=activity`，承载现有通用动态能力，但不占据默认首屏。

### 4.2 上下文规则

复用现有个人、组织和团队上下文切换：

- 个人上下文展示当前用户负责或参与的项目，标题为“我的项目”。
- 组织上下文默认展示组织内全部可见项目，标题为“研发工作台”，并提供“只看我的”。
- 团队上下文只展示该团队可见仓库所关联的项目。
- 多组织数据不在个人首页中混成部门全景；用户通过现有上下文切换选择组织。
- 所有结果继续受现有组织、团队、项目和仓库权限约束。

## 5. 登录首页信息架构

### 5.1 页面头部

页面头部包含：

- 标题“研发工作台”或“我的项目”。
- 说明“查看项目推进、责任归属与研发进展”。
- “团队全景 / 只看我的”切换，仅在组织上下文显示。
- 有权限时显示“新建项目”。

### 5.2 关注摘要

用一行轻量摘要替代四张大指标卡，展示：

- 阻塞项目数。
- 已延期项目数。
- 本周到期项目数。
- 七天以上没有有效研发进展的项目数。
- 未指定负责人的项目数。

点击指标设置对应筛选。摘要基于当前上下文内全部可见活跃项目计算，不能只统计当前分页。

### 5.3 搜索与筛选

提供：

- 搜索项目名称、人员或关联仓库。
- 按阶段、风险和负责人筛选。
- “只看我的”快捷筛选。
- 查看归档项目入口。
- 存在筛选时提供一键清除。

筛选状态使用 URL 查询参数保存，刷新、分页及浏览器前进后退均应保留。

### 5.4 项目排序

默认排序依次为：

1. 已阻塞。
2. 已延期。
3. 需关注。
4. 七天以上没有有效研发进展。
5. 临近目标日期。
6. 正常项目。

同一等级内按下一步行动期限、项目目标日期和最近项目更新时间排序。

## 6. 项目执行单元

首页不再使用高密度总账表格。每个项目以“项目执行单元”呈现，并采用单向阅读结构。

### 6.1 状态头部

第一行回答项目是否正常：

- 项目名称和一行说明。
- 当前阶段。
- 风险状态。
- 项目进度及数据来源。
- 目标日期。
- 项目负责人。
- 项目详情入口。

进度若来自关联主里程碑，应显示“里程碑”；否则显示“手动更新”，避免混淆数据来源。

### 6.2 当前问题与下一步

第二行将管理判断转化为行动：

- 当前问题或本阶段目标。
- 下一步行动。
- 下一步执行人。
- 下一步期限。

阻塞和延期项目必须突出该区域。正常项目没有当前问题时，仅展示阶段目标和下一步。

### 6.3 责任归属

第三行以紧凑形式展示：

- 项目负责人。
- 参与成员。
- 下一步执行人。

人员信息不再与代码进展机械左右分栏。点击成员可按其负责或参与的项目筛选。首页不展示个人提交数、贡献排名或工作量评分。

### 6.4 真实研发进展

项目执行单元最多展示最近三条有效研发进展。进展使用完整横向空间，不在狭窄栏内显示提交列表。

每条进展包含：

- 进展结论。
- 状态：已交付、已合并、已完成、评审中、开发中或受阻。
- 对应仓库及分支。
- 负责人或主要参与人。
- 发生时间。
- PR、Issue、Release 或 Commit 证据链接。
- 可获得时展示构建或验收结果。

### 6.5 展开规则

- 阻塞、延期、需关注和长期无进展项目默认展开。
- 正常项目默认使用紧凑行，只展示状态、负责人、下一步和最近一条有效进展。
- 用户可以展开正常项目，展开状态只在当前会话保存。
- 窄屏下所有区域改为纵向排列，不保留内部多栏。

## 7. “真实研发进展”的定义

“真实研发进展”不是原始提交列表，而是从研发事件中提炼出的项目事实。

### 7.1 事件优先级

按以下顺序选取并展示：

1. Release 发布。
2. 关联主里程碑完成。
3. PR 合并。
4. 关联 Issue 完成。
5. PR 创建、进入评审或评审通过。
6. 关键功能持续开发的提交。
7. 构建失败、PR 长期未处理或长期无有效进展等异常信号。

默认统计最近七天；没有事件时展示最后一次有效进展时间。项目完整代码活动页仍使用更长时间范围。

### 7.2 去噪规则

- 同一 PR 的连续提交合并为一条“开发中”进展。
- 合并提交、纯格式化、机器人依赖更新和重复推送默认折叠。
- Release、合并 PR 和完成 Issue优先于其底层提交，不重复展示同一成果。
- 提交信息无法可靠归纳时展示原始事实，不生成业务结论。
- 只有存在明确的项目、里程碑或 Issue 关联时，才能描述该事件推动了某一阶段或进度。

### 7.3 示例

原始代码事实：

> `fix: 修复权限缓存失效`

首页进展表达：

> 已完成“权限缓存修复”
>
> PR #348 已合并至 `main` · 陈敏 · 两小时前

若 PR 明确关联项目主里程碑，可以附加“计入灰度验证里程碑”；否则不声称该提交改变了项目完成度。

## 8. 人工判断与自动证据

### 8.1 人工维护

负责人维护：

- 项目目标和说明。
- 当前阶段。
- 项目风险。
- 项目负责人和参与成员。
- 当前问题。
- 下一步行动、执行人和期限。
- 项目目标日期。
- 手动进度，仅在未关联主里程碑时使用。

默认项目配置增加以下字段：

- `current_problem`：长文本。
- `next_action`：长文本。
- `next_action_owner`：成员。
- `next_action_due`：日期。

现有 `owner` 和 `followers` 字段继续分别表示负责人和参与成员。

### 8.2 自动聚合

系统从可见的关联仓库聚合：

- 主里程碑完成率。
- Issue 完成及待处理数量。
- 待合并和已合并 PR。
- 最近有效研发进展。
- Release。
- 默认分支的最新构建状态。
- 最后有效活跃时间。

项目可指定一个主里程碑。存在主里程碑时，首页进度使用该里程碑完成率；否则使用项目的手动 `progress` 字段，并明确标记来源。自动数据不回写人工字段。

主里程碑关联以独立关系保存，包含项目 ID、仓库 ID 和里程碑 ID。每个项目最多关联一个主里程碑；所选里程碑必须属于该项目已关联且当前用户可见的仓库。删除仓库关联或里程碑后，项目自动回退到手动进度并显示提示，不保留失效引用。

### 8.3 冲突提示

人工判断与自动证据冲突时同时展示，不静默修正。例如：

- 项目风险为“正常”，但目标日期已经过去。
- 手动进度较高，但主里程碑仍有大量未完成 Issue。
- 阶段为“研发中”，但已发布新的 Release。
- 项目处于活跃状态，但七天内没有有效研发进展。

冲突进入关注摘要，并提示负责人确认项目状态。

## 9. 人员责任视图

首页右侧保留紧凑的“人员责任”视图，用于跨项目查找责任关系，而不是重复项目卡内容：

- 成员姓名。
- 负责项目数。
- 参与项目数。
- 负责项目名称。

点击成员后，主区域筛选其负责或参与的项目。该视图不展示提交数、代码行数、活跃天数或任何绩效评分。窄屏下该视图移动到项目列表之后。

## 10. 项目详情

项目详情从资料页升级为项目执行档案。

### 10.1 首屏

- 项目名称、说明、阶段、风险和目标日期。
- 当前问题。
- 下一步行动、执行人和期限。
- 编辑入口，仅对有权限用户显示。

### 10.2 项目进展

- 当前阶段目标。
- 本周完成事项。
- 待完成事项。
- 进度及来源。
- 主里程碑和关键节点。

### 10.3 责任与协作

- 项目负责人。
- 参与成员。
- 当前下一步执行人。
- 点击成员查看其负责和参与的其他项目。

### 10.4 代码进展与仓库

- 最近有效研发进展时间线。
- PR、Issue、Release 和构建摘要。
- 主仓库和关联仓库角色。
- 仓库最后活动与健康状态。
- “完整代码活动”进入更完整的活动页面。

现有“项目概览、代码活动、变更记录”页签继续保留；概览展示管理摘要和有限进展，代码活动页用于深入查看，变更记录只记录项目资料变更。

## 11. 数据流与组件边界

服务端负责：

- 解析个人、组织和团队上下文。
- 项目查询、排序、筛选和分页。
- 项目、成员、主里程碑和关联仓库的批量读取。
- 仓库、Issue、PR、Release、提交和构建权限过滤。
- 有效研发进展的归并、排序和去噪。
- 关注摘要和冲突检测。

前端负责：

- 工作台展示。
- 正常项目的展开与收起。
- URL 筛选控件的渐进增强。
- 加载、局部错误和空状态展示。
- 响应式布局和可访问交互。

建议组件边界：

- `ProjectWorkbench`：工作台组合与状态。
- `ProjectAttentionBar`：关注摘要。
- `ProjectFilters`：搜索和筛选。
- `ProjectExecutionUnit`：展开和紧凑项目单元。
- `ProjectProgressEvents`：有效研发进展。
- `ProjectResponsibility`：人员责任视图。
- 服务端 query/service：批量工作台查询与进展聚合。

组件只消费明确的服务端数据，不从 DOM 文本或样式反向推断业务状态。

## 12. 权限与隐私

- 用户只能看到有权访问的组织项目和仓库信息。
- 私有仓库的提交、PR、Issue、Release 和构建状态必须在服务端过滤。
- 项目编辑继续复用现有组织项目权限。
- 无编辑权限用户不能修改风险、进度或下一步。
- 汇总数量必须基于过滤后的可见数据，不能泄露不可见仓库的存在。
- 离开组织的成员保留稳定占位，避免项目历史无法理解。

## 13. 空状态与错误处理

- 没有项目：说明工作台用途；有权限时显示“新建项目”，否则提示联系项目管理员。
- 个人未参与项目：提示切换组织上下文或查看全部可见项目。
- 当前组织尚未发布项目配置：说明需要由组织项目管理员完成配置，并仅向有权限用户显示设置入口。
- 项目未指定负责人：显示“待指定负责人”，并进入关注摘要。
- 项目未关联仓库：仍展示管理信息，并提示关联仓库。
- 项目未关联主里程碑：使用手动进度并标记来源。
- 七天内无有效进展：显示最后有效进展时间，不直接判定项目失败。
- 单个仓库活动查询失败：项目管理主体继续展示，代码区域显示“研发进展暂不可用”。
- 工作台项目查询失败：使用标准页面错误，不展示可能不准确的部分项目数据。
- 项目资料超过七天未更新：提示负责人确认状态。
- 并发修改冲突：要求刷新后重试，不静默覆盖。

## 14. 性能要求

- 首页批量查询项目、字段、成员、主里程碑和仓库关联，避免逐项目数据库查询。
- 每个项目最多返回三条有效进展，正常紧凑项目首屏只渲染一条。
- 默认进展窗口为七天，服务端设置全局和单项目上限。
- 代码聚合使用有界查询；缓存键包含用户、上下文和权限相关版本。
- 项目管理主体优先返回。代码聚合可以局部降级，但不能阻塞整个首页。
- 目标是活跃项目少于十个时，工作台在常规内部网络环境下快速完成首屏渲染。

## 15. 响应式与可访问性

- 桌面端使用项目主区域和人员责任侧栏。
- 中等宽度下人员责任移动到项目列表之后。
- 窄屏下项目执行单元改为单列，状态、责任、行动和进展依次排列。
- 不在窄屏保留会挤压提交标题的内部双栏。
- 风险、阶段、构建和进度均使用文字表达，不只依赖颜色。
- 所有筛选、展开、链接和操作支持键盘及清晰的 `:focus-visible` 状态。
- 尊重 `prefers-reduced-motion`，不添加页面进入动画。

## 16. 验证与测试

### 16.1 Go 单元测试

- 个人、组织和团队上下文的项目可见范围。
- 风险优先排序和 URL 筛选。
- “只看我的”同时匹配负责人和参与成员。
- 主里程碑进度与手动进度回退。
- 关注摘要基于全量可见项目，而非当前分页。
- 有效进展优先级、归并、去噪和七天窗口。
- 私有仓库、Issue、PR、Release、提交和构建权限过滤。
- 人工判断与自动证据冲突检测。
- 批量查询不产生随项目数线性增长的数据库查询。

### 16.2 前端测试

- 异常项目默认展开，正常项目默认紧凑。
- 项目状态、责任、下一步和进展的展示顺序。
- 进度来源标签。
- 成员点击筛选。
- 无项目、无仓库、无里程碑、无进展和局部错误状态。
- 窄屏单列布局和长提交标题。

### 16.3 浏览器验收

- 登录首页不再显示贡献热力图、通用“无活动”和仓库侧栏。
- 个人、组织和团队上下文切换正确。
- 桌面、当前浏览器宽度和移动宽度均无主要内容裁切或横向溢出。
- 核心路径可用：筛选项目、查看负责人、展开正常项目、进入项目详情、打开进展证据。
- 亮色和暗色主题均保持清晰层级。

## 17. 不在本次范围

- 甘特图和拖拽看板。
- 工时统计和资源排期。
- 人员绩效、贡献排名和代码行数统计。
- 自动生成业务结论或使用提交数量判断项目健康度。
- 通知、订阅和自动催办系统。
- 重构 Gitea 全局导航或仓库、Issue、PR 的原生页面。
- 删除原有用户资料页热力图或底层活动数据。

## 18. 成功标准

上线后通过定性可用性检查和产品埋点验证：

- 用户能在十秒内找到项目负责人、当前风险和下一步行动。
- 从登录首页进入目标项目详情的操作不超过两次点击。
- 用户无需进入仓库即可判断最近是否存在有效研发进展。
- 风险项目均能定位到责任人或明确显示“待指定负责人”。
- 首页不出现因代码权限过滤而泄露的项目或仓库信息。
- 登录首页项目主体可用时，单个代码聚合失败不会导致整页不可用。
