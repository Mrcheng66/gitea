# Gitea 原生项目管理与定制化重构设计

日期：2026-08-05  
状态：已确认，待实施计划  
基线：Gitea v1.27.1

## 1. 背景

当前系统由 Gitea 和独立 Workbench 组成。Gitea 提供用户、组织、团队、仓库、权限、代码、Issue 和合并请求；Workbench 通过独立 Go 服务、Vue 应用、OAuth 会话、SQLite 数据库和 Nginx 路由提供项目档案、成员与代码汇总。

Workbench 解决了项目状态管理问题，但也形成了明显割裂：

- 同一个研发平台存在两套应用壳、导航和页面语言。
- Workbench 重新处理 Gitea 身份、会话、权限和同步状态。
- 项目直接以 `repo_id` 为身份，无法独立存在或关联多个仓库。
- 阶段、风险、负责人、跟进人、日期、进度和说明在数据库、Go、API、TypeScript 和表单中重复硬编码。
- 字段、视图、指标和导航的调整都需要发布代码。

本次重构不继续为 Gitea 增加外置管理壳，而是直接维护 Gitea Fork，将项目管理和核心配置能力实现为 Gitea 原生模块。

## 2. 已确认的产品边界

### 2.1 交付模式

系统服务一个内部研发团队，不建设多租户、计费、白标或 SaaS 租户隔离能力。

### 2.2 项目与仓库

项目是独立领域对象：

- 项目可以不关联仓库。
- 项目可以关联一个或多个 Gitea 仓库。
- 仓库可以作为项目的主仓库或关联仓库。
- 代码、Issue、合并请求、Release 和仓库设置仍由 Gitea 原生仓库页面承担。

### 2.3 首期定制能力

首期只实现核心配置层：

- 项目动态字段。
- 枚举选项和字段校验。
- 项目列表列、筛选器和排序。
- 项目工作台指标。
- 项目相关导航。
- 配置草稿、校验、发布、版本历史和回滚。

首期不实现：

- 任意业务对象。
- 流程编排引擎。
- 自定义公式。
- 自定义 SQL。
- 自定义脚本。
- 通用低代码页面搭建。
- 多租户与租户级配置。

### 2.4 切换方式

允许一次性维护窗口。现有项目档案需要迁移，但旧 Workbench 页面、API、OAuth 会话和路由不要求长期兼容。

### 2.5 配置方式

配置通过产品内的组织设置页面维护，不以 YAML 或 JSON 文件作为日常管理入口。

## 3. 源码与版本策略

### 3.1 仓库主体

Gitea v1.27.1 源码成为仓库主体，完整保留官方 Git 历史。

Git 关系固定为：

- `origin`：团队维护的定制 Fork。
- `upstream`：官方 `go-gitea/gitea` 仓库，仅用于查阅和安全补丁来源。
- 定制主分支：团队长期维护的产品分支。
- 基线标签：`v1.27.1`。

当前仓库中的部署、备份、恢复和验收资产统一迁移到 Gitea 源码仓库的 `ops/`。旧 `workbench/` 在迁移验收通过后退出生产路径；具体删除文件将在实施计划中列出并再次确认。

### 3.2 固定版本策略

功能版本固定在 Gitea v1.27.1：

- 不主动合并后续 Gitea 功能版本。
- 锁定 Go、Node、前端依赖和构建环境。
- 只人工回移高危安全修复和必要兼容修复。
- 每个回移补丁独立记录官方来源、影响范围、测试证据和回滚方法。
- 保留 Gitea MIT 许可证和版权声明。

固定版本降低了长期合并冲突，但团队必须持续跟踪安全公告。固定版本不等于停止安全维护。

## 4. 总体架构

系统保持模块化单体：一个 Gitea 进程、一个数据库、一套身份权限、一套页面框架和一条构建部署链路。

### 4.1 保持上游语义的区域

以下 Gitea 核心能力不重新实现：

- 用户、组织、团队和身份会话。
- 仓库、分支、提交和 Git 协议。
- Issue、合并请求和 Release。
- 仓库与组织权限。
- API 认证、Web 请求上下文和 CSRF 保护。
- 数据库引擎、迁移框架和资源构建方式。

### 4.2 新增原生模块

定制能力按 Gitea 既有代码结构组织：

- `models/project`：项目、仓库关联、字段值、配置版本和变更记录。
- `services/project`：项目用例、字段验证、配置发布、回滚和指标查询。
- `routers/web/project`：项目中心、项目详情和配置中心页面路由。
- `routers/api/v1/project`：项目与配置 API。
- `templates/project`：服务端页面结构和原生页面集成。
- `web_src/js/project`：动态字段、配置编辑、列表和工作台交互。
- 对应的 locale、CSS 和测试文件。

以上名称表示必须保持的逻辑模块边界。拉取 v1.27.1 后，实施计划会将逻辑模块逐一映射到该版本的实际包路径；不得因为现有目录结构而重新混合这些职责。

### 4.3 受控接入点

允许对上游核心做少量、明确的接入修改：

- 顶部导航增加“项目”。
- 组织页面和组织设置增加项目入口。
- 仓库页面增加所属项目入口。
- 路由注册项目 Web 与 API 端点。
- 权限注册项目读取、编辑和配置能力。
- 原生迁移序列增加项目模块数据表。

除上述入口外，不修改仓库、Issue、合并请求和 Git 核心流程。

## 5. 信息架构

### 5.1 配置边界

组织是项目与配置边界：

- 每个项目必须归属一个 Gitea 组织。
- 项目字段、视图、指标和配置版本均归属该组织。
- 组织 Owners 管理配置。
- 项目编辑团队维护项目内容。
- 普通组织成员读取已发布配置下的项目数据。

首期不支持用户个人项目和跨组织项目。

### 5.2 顶部导航

原生顶部导航包含：

- 工作台。
- 项目。
- Issue。
- 合并请求。
- 探索。

“项目”进入当前组织或默认组织的项目空间，不打开第二套应用。

### 5.3 项目页面

组织项目空间包含：

- 项目工作台：配置驱动的指标和重点列表。
- 全部项目：配置驱动的列、筛选器和排序。
- 新建项目：固定字段和动态字段表单。
- 项目详情：概览、动态字段、关联仓库、代码活动汇总和变更记录。

### 5.4 配置中心

组织设置中的“项目配置”包含：

- 字段与选项。
- 列表视图与默认筛选器。
- 工作台指标。
- 草稿校验与发布。
- 配置版本历史与回滚。

普通成员不读取草稿，只读取当前已发布版本。

## 6. 数据模型

### 6.1 `project`

保存稳定系统字段：

- `id`：项目主键。
- `owner_id`：所属组织 ID。
- `slug`：组织内稳定标识。
- `name`：项目名称。
- `description`：项目说明。
- `lifecycle`：`active` 或 `archived`。
- `version`：乐观并发版本。
- Gitea 标准创建人、创建时间和更新时间字段。

阶段、风险、进度、负责人、跟进人和目标日期不是固定数据库列，而是默认配置创建的动态字段。

### 6.2 `project_repository`

保存项目与原生仓库的关系：

- `project_id`。
- `repository_id`。
- `role`：`primary` 或 `related`。
- `created_by`。
- 创建时间。

一个项目最多有一个主仓库，可以有多个关联仓库。数据库约束保证同一项目不能重复关联同一仓库。

### 6.3 `project_field_value`

动态字段使用类型化值表，而不是把所有项目数据存入一个 JSON 文档。

主要字段：

- `project_id`。
- `field_key`。
- `value_text`。
- `value_number`。
- `value_time`。
- `value_bool`。
- `value_user_id`。
- `value_json`，仅用于成员数组和多选值等受控复合类型。

每条记录只能使用与字段类型对应的值列。服务层负责类型约束，数据库增加适用的唯一键与查询索引。

类型化存储支持按阶段、风险、成员、数值和日期进行筛选、排序、分组与统计，同时避免为每个新字段修改数据库结构。

### 6.4 `project_config_version`

保存完整配置快照：

- `id`。
- `owner_id`。
- 递增 `version`。
- `state`：`draft` 或 `published`。
- `payload`：字段、选项、列表、筛选器和指标的完整 JSON 快照。
- 创建人、创建时间、发布人和发布时间。

已发布版本不可原地修改。

### 6.5 `project_config_pointer`

每个组织一条指针记录：

- `owner_id`。
- `draft_version_id`。
- `published_version_id`。
- `version`，用于发布并发控制。

发布配置时，在一个数据库事务中创建不可变版本并切换 `published_version_id`。发布失败时仍指向旧版本。

### 6.6 `project_change_log`

记录项目变更：

- 项目与操作者。
- 请求标识。
- 变化字段键。
- 变更前后值。
- 变更时间。
- 来源，例如 `web`、`api` 或 `legacy-import`。

## 7. 字段与配置规则

### 7.1 支持的字段类型

- 短文本。
- 长文本。
- 单选。
- 多选。
- 整数。
- 小数。
- 百分比。
- 日期。
- 日期时间。
- 布尔值。
- 组织成员。
- 组织成员数组。

仓库关联由 `project_repository` 管理，不实现为普通动态字段。

### 7.2 稳定字段键

- `field_key` 是字段的永久身份。
- 显示名称可以修改。
- 字段发布后不能修改 `field_key`。
- 删除字段只将定义标记为归档，不立即删除历史值。
- 已有数据的字段不能直接变更为不兼容类型。
- 不兼容变更必须创建新字段，并通过显式数据迁移完成。

### 7.3 发布校验

发布前必须校验：

- 字段键唯一且格式合法。
- 字段类型和默认值兼容。
- 必填字段存在可执行的默认或迁移策略。
- 枚举选项键唯一。
- 列表列、筛选器和指标引用的字段存在且未归档。
- 字段删除和类型变化不破坏现有数据。
- 指标仅使用支持的聚合和分组方式。

### 7.4 查询边界

配置不包含原始 SQL。列表与指标通过类型感知的查询构建器生成参数化查询。

首期允许：

- 等于或不等于。
- 包含。
- 为空或非空。
- 数字和日期范围。
- 成员匹配。
- 计数。
- 按枚举、成员或布尔字段分组。
- 数字字段平均值。

## 8. 权限模型

### 8.1 角色

- 组织成员：读取项目公共字段。
- 项目编辑团队：创建和编辑项目。
- 组织 Owners：拥有项目编辑能力，并管理、发布和回滚配置。

项目编辑团队沿用可配置团队名称，初始值从当前 `GITEA_EDITOR_TEAMS` 迁移或由组织 Owner 设置。

### 8.2 仓库权限

项目页面不能扩大仓库权限：

- 用户只能看到其有权访问的关联仓库。
- 代码活动汇总只包含用户可访问仓库的数据。
- 添加仓库关联时，操作者必须有项目编辑权限且能访问目标仓库。
- 无权访问的仓库不返回名称、路径、提交数量或其他身份信息。

### 8.3 API

项目 Web 和 API 路由使用 Gitea 原生身份上下文、会话、Token、CSRF 和权限检查。项目 API 不建立第二套认证机制。

项目模块在 Gitea 原生 Token Scope 注册表中增加 `read:project` 和 `write:project`：

- 读取项目 API 需要 `read:project` 或更高权限，并继续检查组织成员身份。
- 写入项目 API 需要 `write:project`，并继续检查项目编辑团队或组织 Owner 身份。
- 配置发布与回滚只允许组织 Owner；Token Scope 不能单独绕过组织角色。

## 9. 运行数据流

项目写入顺序：

1. Gitea 请求上下文识别当前用户、组织和请求来源。
2. 权限层检查组织角色、项目编辑团队和仓库可见性。
3. 配置服务读取组织当前已发布配置版本。
4. 验证器按字段类型、必填、选项和范围规则校验输入。
5. 服务层在一个事务中写入项目、字段值、仓库关联和项目版本。
6. 审计服务记录操作者、变化字段及前后值。

列表读取顺序：

1. 加载组织当前已发布视图配置。
2. 验证用户组织成员身份。
3. 查询构建器将配置编译成参数化查询。
4. 加载项目固定字段和动态字段值。
5. 仓库关联与代码活动按当前用户仓库权限裁剪。
6. 返回服务端模板或 API DTO。

## 10. 错误处理

- `404`：项目、仓库或组织不可见时统一返回不存在，避免资源泄露。
- `403`：资源可见但操作权限不足。
- `409`：项目版本或配置版本冲突，并返回当前版本信息。
- `422`：动态字段验证失败，错误包含稳定 `field_key` 和用户可读说明。
- `500`：数据库或配置发布失败；发布事务不切换运行版本。

配置草稿永远不能被成员运行页面读取。发布失败、进程重启或缓存失效都不能产生半发布状态。

## 11. 一次性迁移

### 11.1 迁移范围

旧 Workbench 中存在 `project_profiles` 的记录迁移为新项目：

- 项目名称和说明来自关联 Gitea 仓库。
- 原仓库关联为主仓库。
- `stage`、`progress`、`owner_user_id`、`follower_user_ids`、`start_date`、`target_date`、`risk` 和 `summary` 映射到默认动态字段。
- 旧 `project_audit_events` 转换为来源为 `legacy-import` 的变更记录。

没有 `project_profiles` 的仓库不自动创建项目。组织 Owner 可以在新系统中从仓库新建项目或批量导入。

不迁移：

- Workbench OAuth 会话。
- Workbench Gitea 用户、仓库和提交缓存。
- Workbench 同步状态。

这些信息由 Gitea 原生数据库和会话直接提供。

### 11.2 切换步骤

1. 固定源码与依赖并构建定制 Gitea。
2. 在生产数据副本上运行迁移预检，输出项目数量、仓库匹配、用户匹配、冲突和缺失报告。
3. 完整备份 Gitea 数据库、仓库存储、配置、附件和旧 Workbench 数据库。
4. 进入维护窗口，停止 Gitea 与 Workbench 写入。
5. 运行 Gitea 原生数据库迁移。
6. 运行一次性 Workbench 导入工具。
7. 核对项目、字段、成员、仓库关联、权限和审计数量。
8. 启动单一 Gitea Fork，移除 Workbench 路由分流。
9. 完成登录、仓库、Git HTTPS、项目中心和配置发布验收。

### 11.3 回滚

切换后保留明确回滚窗口。若验收失败：

1. 停止定制 Gitea。
2. 恢复切换前 Gitea 数据库和文件备份。
3. 恢复旧 Gitea 与 Workbench 服务和 Nginx 路由。
4. 不尝试把新系统产生的数据反向同步回旧 Workbench。

因此，完成切换验收前必须限制新系统写入范围并缩短验收时间。

## 12. 视觉与交互方向

保留根目录 `design.md` 中已确认的研发工具方向：

- `modern-minimal`。
- Geist 与 Geist Mono。
- 浅色、中性纸面和克制绿色锚点。
- 4pt 间距体系。
- 稳定尺寸的表格、工具栏和控件。
- 克制动效和完整焦点状态。
- 不使用营销式页面、装饰卡片、渐变标题或多层阴影。

实现时需要将这套设计系统适配到 Gitea v1.27.1 的原生模板、CSS 变量和 Vue 组件，而不是继续通过外部应用壳覆盖。仓库、Issue 和合并请求页面保持原生信息架构，只统一品牌、导航、颜色、字体、控件和间距。

## 13. 测试策略

### 13.1 领域单元测试

- 项目状态与归档规则。
- 字段类型、默认值和校验。
- 配置兼容检查。
- 查询运算符与指标定义。
- 权限决策。

### 13.2 数据库集成测试

- 新迁移在 Gitea 支持的测试数据库上执行。
- 配置发布与回滚事务。
- 类型化值写入和查询。
- 项目和配置并发版本冲突。
- 仓库关联唯一性与主仓库约束。

本次交付的项目模块明确只支持 SQLite，与当前生产部署一致。项目模块启用时若检测到非 SQLite 数据库，进程启动失败并返回明确配置错误。Gitea 未启用项目模块时不改变其原生数据库行为。

### 13.3 权限矩阵测试

- 非组织成员。
- 普通组织成员。
- 项目编辑团队成员。
- 组织 Owner。
- 可见和不可见私有仓库。
- API Token 与 Web 会话。

### 13.4 页面与 API 测试

- 项目创建、编辑、归档和并发冲突。
- 动态字段错误定位。
- 仓库关联和权限裁剪。
- 配置草稿、校验、发布和回滚。
- 配置驱动列表、筛选器和指标。
- 空状态、失败状态和移动端布局。

### 13.5 迁移与验收测试

- 在生产数据副本上进行至少一次完整演练。
- 迁移前后项目、字段值、仓库关联和审计数量核对。
- Gitea 登录、组织、仓库、Git HTTPS、Issue 和合并请求回归。
- 备份恢复和旧路由回滚演练。

## 14. 实施阶段建议

实施计划应拆分为以下阶段，每阶段可独立验证：

1. 建立保留历史的 Gitea v1.27.1 Fork 和可重复构建基线。
2. 移植现有品牌与运维资产，证明未增加项目功能时核心 Gitea 回归通过。
3. 增加项目固定模型、仓库关联、权限和原生页面入口。
4. 增加动态字段、类型化值和项目审计。
5. 增加组织配置草稿、校验、发布和回滚。
6. 增加配置驱动列表、筛选器和工作台指标。
7. 开发 Workbench 预检与一次性导入工具。
8. 在生产数据副本上演练迁移、验收和回滚。
9. 执行维护窗口切换并退役旧 Workbench 生产路径。

## 15. 成功标准

重构完成需同时满足：

- 用户只面对一套 Gitea 原生导航、登录和页面框架。
- 项目可以独立存在，并关联零个、一个或多个仓库。
- 组织 Owner 可以不改代码地配置字段、选项、列表、筛选器和指标。
- 配置修改必须经过草稿和发布，不影响正在运行的版本。
- 项目编辑不绕过组织和仓库权限。
- 已配置的旧 Workbench 项目档案与审计数据完成迁移。
- Gitea 登录、Git、仓库、Issue 和合并请求核心能力无回归。
- 迁移过程有可验证的预检报告、完整备份和可执行回滚方案。
- 固定版本的构建、依赖和安全补丁流程有书面记录。

## 16. 明确拒绝的方向

- 不继续构建外置 Workbench 应用壳。
- 不长期运行 Gitea 与新项目模块的双写。
- 不将每个仓库自动等同为项目。
- 不复制 Gitea 用户、组织、仓库和权限模型。
- 不建设微服务架构。
- 不建设通用低代码平台。
- 不允许配置执行任意 SQL、公式或脚本。
- 不在首期实现多租户、计费或白标。
