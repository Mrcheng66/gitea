# Gitea 研发管理壳设计

- 日期：2026-08-03
- 状态：待书面审阅
- 目标：在不 fork Gitea 的前提下，将研发管理视图与 Gitea 代码能力融合为单域名、单入口的内部平台
- 目标用户：研发部门内部成员

## 1. 背景

现有系统是面向十人以内团队的轻量 Gitea 部署。Gitea 能稳定承担仓库、代码、提交、权限和 Git 协议，但登录后的默认工作台更偏个人仓库活动，无法直接回答团队最关心的三个问题：

1. 各项目当前处于什么阶段，进展和风险如何。
2. 最近代码发生了什么变化。
3. 团队成员最近参与了哪些项目。

本设计在 Gitea 外增加独立管理壳，但通过同一域名、统一登录、统一导航和统一视觉，将两部分呈现为一套产品。Gitea 继续作为代码引擎，管理壳负责项目与团队管理视图。

## 2. 目标与非目标

### 2.1 目标

- 将工作台首页改为以项目状态为主、最近代码为辅、成员动态独立的研发视图。
- 提供易修改的项目档案，包括阶段、进度、负责人、跟进人、计划日期、风险和说明。
- 所有研发成员均可编辑项目档案，每次修改可追踪。
- 保持现有 HTTPS 和 SSH clone 地址不变。
- 复用 Gitea 用户、组织、仓库权限和代码数据，不建立第二套账号体系。
- 保持 Gitea 可独立升级，不修改其核心源码和数据库。
- 为以后增加看板、通知或报表保留稳定 API 与数据库迁移边界。

### 2.2 非目标

- 第一阶段不实现 Issue、任务看板、通知、审批、工时和复杂报表。
- 不重新开发代码浏览、提交详情、合并请求和仓库设置。
- 不把完整 Git 历史复制到管理壳数据库。
- 不引入 PostgreSQL、消息队列、缓存集群或独立身份服务。
- 不在 Gitea 上游源码中长期维护私有 fork。

## 3. 方案决策

采用独立 Sidecar 管理壳：

- Vue 3 + TypeScript 实现管理界面。
- Go 实现 HTTP 服务、Gitea OAuth/API 集成、项目档案 API、同步和审计。
- Vue 构建产物嵌入 Go 二进制，运行时只增加一个容器。
- 工作台使用独立 SQLite，不读取或写入 Gitea 数据库。
- 宿主机 Nginx 在同一域名下按路径将请求分发给管理壳或 Gitea。

未采用纯前端方案，因为浏览器直接调用 Gitea API 会使令牌、跨仓库写入和错误处理变得脆弱。未采用 Gitea fork，因为模板和 Go 代码的长期分叉会显著增加升级成本。

## 4. 系统架构

```text
浏览器
  |
  v
Nginx · git.ghgmall.cn
  |-- 管理壳页面与 API ----------> Workbench Go + embedded Vue
  |                                      |-- SQLite 项目档案与审计
  |                                      `-- OAuth/API ----------+
  |                                                               |
  `-- 其他页面与 Git HTTPS ------> Gitea <------------------------+
                                          |
                                          `-- 仓库 / 用户 / 权限 / 提交

Git SSH :2222 ---------------------------> Gitea
```

### 4.1 组件职责

| 组件 | 职责 | 不承担 |
| --- | --- | --- |
| 宿主机 Nginx | TLS、单域名入口、路径分发 | 业务鉴权和数据聚合 |
| Workbench Vue | 工作台、项目、成员、最近代码和编辑交互 | 直接保存 OAuth 令牌 |
| Workbench Go | 会话、Gitea API、权限校验、项目档案、同步、审计 | Git 协议和代码解析 |
| Workbench SQLite | 项目档案、编辑历史、会话、最近同步缓存 | Gitea 用户密码和完整 Git 历史 |
| Gitea | 用户、组织、仓库权限、Git、提交、合并请求和设置 | 项目进展与管理视图 |

## 5. 单域名路由

Nginx 按以下顺序匹配：

| 路径 | 所有者 |
| --- | --- |
| `GET /` | Workbench 工作台 |
| `/projects`、`/projects/*` | Workbench 项目列表与详情 |
| `/people`、`/people/*` | Workbench 成员列表与详情 |
| `/activity`、`/activity/*` | Workbench 最近代码与活动 |
| `/_workbench/*` | Workbench 静态资源、API 和 OAuth 回调 |
| 其他全部路径 | Gitea |

`projects`、`people`、`activity` 和 `_workbench` 是保留的顶级路径，不允许创建同名 Gitea 用户或组织。仓库路径如 `/admin1/task`、Gitea 的 `/user/*`、`/explore/*`、`/api/*` 和 Git HTTPS 请求保持原样，因此现有 clone 地址无需修改。

如果管理壳回滚，移除 Workbench 的 Nginx 路由即可恢复由原 `location /` 将根路径交给 Gitea，其他 Gitea 路径和数据不受影响。

## 6. 身份与权限

### 6.1 登录

1. 未登录用户访问管理壳。
2. 管理壳跳转到 Gitea OAuth2 授权端点。
3. 用户在 Gitea 完成登录和授权。
4. Gitea 回调 `/_workbench/auth/callback`。
5. Go 服务创建服务端会话并设置 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie。

OAuth 访问令牌由服务端加密保存，不进入浏览器持久存储、日志或错误响应。会话退出时撤销或删除对应令牌。

### 6.2 可见性

- 用户只看到其 Gitea 账号有权访问的仓库。
- 管理壳保存用户最近一次可访问仓库集合，用于 Gitea 短暂不可用时的降级展示。
- 降级期间不得展示用户最近一次权限集合之外的仓库缓存。

### 6.3 编辑权限

- `WORKBENCH_ORG` 指定受管理组织。
- `WORKBENCH_EDIT_TEAMS` 默认包含 `Owners,Developers`。
- 组织内研发成员均可编辑其可见项目的项目档案。
- 负责人和跟进人必须是仍在受管理组织内、且能够访问该仓库的成员。
- 仓库创建、删除和 Gitea 设置仍遵循 Gitea 自身权限，不由管理壳放宽。

所有写请求要求有效会话、CSRF 校验、组织/团队校验和仓库可见性校验。

## 7. 数据模型

### 7.1 `project_profiles`

| 字段 | 说明 |
| --- | --- |
| `repo_id` | Gitea 仓库 ID，主键 |
| `stage` | `planned`、`development`、`testing`、`released`、`paused` |
| `progress` | 0 到 100 的整数 |
| `owner_user_id` | 负责人 Gitea 用户 ID，可为空 |
| `target_date` | 计划日期，可为空 |
| `risk` | `normal`、`attention`、`blocked` |
| `summary` | 项目说明，限制长度 |
| `version` | 乐观锁版本号 |
| `created_at`、`updated_at` | 创建和更新时间 |
| `updated_by` | 最近编辑者 Gitea 用户 ID |

仓库首次同步但还没有项目档案时，工作台显示“未设置”，不自动猜测负责人、阶段或进度。成员第一次保存表单时创建档案。仓库重命名不影响关联，因为主键使用稳定的 Gitea 仓库 ID。

### 7.2 `project_followers`

以 `repo_id + user_id` 为联合主键，保存一个项目的零到多个跟进人。

### 7.3 `project_audit_events`

记录仓库、操作人、时间、变更字段、修改前值、修改后值和请求标识。记录只追加，不通过普通业务 API 修改或删除。

### 7.4 同步缓存

- `gitea_users_cache`：用户 ID、登录名、显示名和头像地址。
- `gitea_repos_cache`：仓库 ID、路径、描述、默认分支、可见性和更新时间。
- `gitea_recent_commits_cache`：每个仓库最近 20 条或最近 30 天的提交摘要，以先达到的限制为准。
- `user_repo_access_cache`：用户最近一次可访问的仓库集合。
- `sync_state`：用户同步游标、最近成功时间和最近错误。

缓存用于性能和短时降级，不作为 Gitea 数据的权威来源，也不保存完整 Git 历史。

## 8. 数据流

### 8.1 读取工作台

1. Go 服务验证当前会话。
2. 检查用户 Gitea 数据缓存是否在 60 秒有效期内。
3. 缓存过期时使用用户 OAuth 令牌增量读取仓库、最近提交和组织成员。
4. 将 Gitea 数据与 `project_profiles`、`project_followers` 合并。
5. 返回项目状态、最近代码、成员动态和同步状态。

同一用户的并发刷新合并为一个请求，避免首页多次触发相同 Gitea API 调用。只有最近活跃的会话会按 60 秒有效期刷新；没有活跃用户时不持续轮询 Gitea。

### 8.2 编辑项目档案

1. 客户端提交字段和当前 `version`。
2. 服务端重新校验组织成员身份和仓库可见性。
3. 在一个 SQLite 事务中更新项目档案、跟进人和审计记录。
4. `version` 不匹配时返回 `409 Conflict` 和最新数据，不覆盖他人修改。
5. 保存成功后返回新版本，客户端在当前行内更新并显示静默成功状态。

### 8.3 进入 Gitea 页面

仓库名、提交标题和提交哈希生成 Gitea 原生深链。Nginx 将这些路径交给 Gitea，顶部导航和主题保持一致，用户不感知系统切换。

## 9. Workbench API

第一阶段 API 保持内部、同源和最小化：

| 方法与路径 | 作用 |
| --- | --- |
| `GET /_workbench/api/me` | 当前用户、团队和能力 |
| `GET /_workbench/api/dashboard` | 工作台聚合数据 |
| `GET /_workbench/api/projects` | 项目列表、筛选和分页 |
| `GET /_workbench/api/projects/:repoId` | 项目详情 |
| `PATCH /_workbench/api/projects/:repoId` | 更新项目档案，要求版本号 |
| `GET /_workbench/api/people` | 成员及其项目和近期活动 |
| `GET /_workbench/api/activity` | 跨项目最近提交 |
| `POST /_workbench/api/sync` | 当前用户手动刷新 |

错误响应使用稳定错误码、用户可读消息和请求标识，不将上游响应正文或令牌返回前端。

## 10. 页面与交互

### 10.1 工作台

- 顶部应用栏：工作台、项目、成员、最近代码、探索，以及搜索、新建项目和用户菜单。
- 主区域：项目状态表，字段为项目信息、阶段、进展、负责人、跟进人、最近代码和操作。
- 次区域：左侧最近代码，右侧独立成员动态。
- 支持搜索、阶段筛选和按最近更新、进度或名称排序。
- “编辑资料”打开项目档案表单，保存后在原位置反馈，不跳转页面。

### 10.2 项目页面

- 项目列表提供完整筛选、排序、分页和空状态。
- 项目详情显示档案、仓库摘要、进展变更和最近代码。
- 代码、提交、合并请求和设置均深链到 Gitea。

### 10.3 成员页面

- 以成员列表展示参与项目、角色和最近活动。
- 不建立第二套成员资料，名称和头像来自 Gitea。

### 10.4 最近代码页面

- 按时间排序，支持项目、成员和分支筛选。
- 每条记录显示仓库、提交信息、哈希、分支、作者和时间。

### 10.5 视觉规范

以根目录 `design.md` 为唯一来源。应用使用现代、克制、高密度的 Workbench 结构；绿色作为品牌和进度信号，蓝色作为代码链接；不使用装饰性大卡片、渐变、玻璃效果或无意义动效。

## 11. 同步、缓存与异常处理

- 正常读取优先返回 60 秒内缓存，并异步刷新临近过期的数据。
- 用户可手动刷新；同一用户同时只执行一个同步任务。
- Gitea 不可用时，显示最近成功同步时间和“数据可能已过期”，仅展示该用户最后已知可见范围。
- 项目档案数据库不可写时，所有编辑入口禁用并说明原因；不得假装保存成功。
- OAuth 失效时清理管理壳会话并重新授权，不无限重试。
- Gitea API 限流时遵循退避，返回可重试时间。
- 编辑冲突返回最新字段，允许用户比较后重新提交。
- 数据库迁移失败时 Workbench 健康检查失败，容器不进入可接流量状态。

## 12. 部署与运维

### 12.1 Compose

增加固定版本 `workbench` 服务：

- 仅连接内部 Docker 网络，不直接映射公网端口。
- 挂载独立数据目录保存 SQLite、会话和迁移状态。
- 依赖 Gitea 健康，但 Gitea 不反向依赖 Workbench。
- 设置 CPU、内存和日志轮转边界。

### 12.2 配置

敏感项通过宿主机私密环境文件注入：

- OAuth Client ID 与 Secret。
- 会话签名与令牌加密密钥。
- 受管理组织和可编辑团队。
- SQLite 路径、同步间隔和缓存限制。

### 12.3 Gitea 定制

- 挂载自定义主题 CSS、字体和品牌资源。
- 只在必要时覆盖导航扩展模板，不修改 Gitea 核心源码。
- 每次 Gitea 升级前对自定义模板和关键页面执行兼容性测试。
- 若模板不兼容，可暂时回退到 Gitea 默认导航，不阻断 Git 和代码浏览。

### 12.4 备份

现有备份扩展为同时包含 Gitea 和 Workbench 数据。备份窗口内停止 Workbench 与 Gitea，归档两个持久化目录和必要部署配置，验证后再上传 COS。恢复文档必须覆盖管理壳 SQLite、OAuth 配置和宿主机 Nginx 路由恢复。

### 12.5 健康检查

- Workbench 存活和就绪端点。
- SQLite 可读写和迁移版本。
- Gitea 健康接口。
- OAuth 配置完整性。
- 最近一次成功同步时间。
- Nginx 的根路径、Workbench API 和 Gitea 仓库路径分发。

## 13. 测试策略

### 13.1 Go

- 数据校验、权限判断、乐观锁、审计和缓存的单元测试。
- 使用模拟 Gitea API 覆盖登录、仓库可见性、同步、限流和上游失败。
- SQLite 迁移前进测试和从空库启动测试。
- API 契约和错误码测试。

### 13.2 Vue

- 项目表、筛选、表单、冲突、权限不足、空状态和失败状态的组件测试。
- API 类型由共享 OpenAPI 或生成类型约束，避免前后端字段漂移。

### 13.3 浏览器与路由

- 登录后打开工作台、筛选项目、编辑资料、查看审计、进入 Gitea 提交详情。
- 320、375、414、768 和桌面视口的无重叠、无页面级横向滚动检查。
- Nginx 验证 `/` 进入 Workbench、`/admin1/task` 进入 Gitea、Git HTTPS clone 不受影响。
- Gitea 不可用、OAuth 过期和编辑冲突的端到端测试。

### 13.4 运维

- Compose 渲染、镜像固定、密钥扫描和 Shell 检查。
- 备份成功、上传失败、恢复后 Workbench 与 Gitea 数据一致性验证。
- Gitea 升级前后自定义主题关键页面截图比较。

## 14. 验收标准

1. 用户访问 `git.ghgmall.cn/` 看到管理工作台，并可使用 Gitea 账号完成登录。
2. 工作台以项目状态为主，显示阶段、进度、负责人、跟进人和最近代码。
3. 最近代码和成员动态分别显示，且可以进入独立页面筛选。
4. 组织内研发成员可以编辑可见项目档案，非成员或无仓库权限用户被拒绝。
5. 两人同时编辑时，旧版本提交返回冲突，不覆盖新版本。
6. 每次项目档案修改记录编辑人、时间和前后值。
7. 点击仓库和提交链接进入统一主题的 Gitea 页面，无需重复登录。
8. 现有 HTTPS 与 SSH clone 地址保持可用。
9. Gitea 短暂不可用时，仅展示用户最后已知可见数据，并明确标记过期状态。
10. Workbench 可独立回滚，回滚后 Gitea 的 Git 和 Web 功能继续可用。
11. 备份和恢复覆盖两套持久化数据，恢复后项目档案与 Gitea 仓库关联正确。
12. 桌面与移动端关键流程无内容重叠，键盘操作和焦点状态可见。

## 15. 第一阶段交付边界

第一阶段只实施：单域名融合、OAuth、统一导航与主题、工作台、项目列表、项目详情、成员列表、最近代码、项目档案编辑、审计、同步缓存、备份与健康检查。

后续模块必须通过 Workbench API 和数据库迁移扩展，不直接向 Gitea 数据库增加表或字段。
