# 十人以内小团队代码管理平台设计

- 日期：2026-08-02
- 状态：已确认
- 变更：2026-08-03 移除外部通知，失败状态仅写入 systemd journal
- 目标环境：公网 Linux 云服务器，Docker Compose

## 1. 背景与目标

为十人以内的小团队提供一套自托管代码管理平台。平台只承担 Git 代码托管、成员管理和基础仓库权限，不建设复杂的代码审核、CI/CD 或项目协作体系。

设计目标：

- 部署和日常维护简单，单台云服务器即可运行。
- 默认保护私有代码，公网访问采用 HTTPS 和 SSH 密钥认证。
- 支持浏览仓库、创建仓库、clone、pull、push、分支和标签等基本操作。
- 每天将完整数据备份到腾讯云 COS，并能按文档在新服务器恢复。
- 控制资源与运维成本，不为未来规模提前引入不必要组件。

## 2. 范围

### 包含

- 用户、组织和团队管理。
- 私有 Git 仓库及 Web 浏览界面。
- HTTPS 与 SSH 两种 Git 访问方式。
- 基础分支保护、操作日志和管理员配置。
- 每日 COS 备份、备份校验、失败状态日志和恢复文档。
- 服务健康、磁盘容量、证书和备份状态检查。

### 不包含

- 强制合并请求、审批人数、CODEOWNERS 等复杂审核门禁。
- CI/CD、Runner、制品库和容器镜像仓库。
- Issue、Wiki、看板、项目管理等协作功能。
- 高可用集群、数据库集群和跨地域热备。
- 周期性恢复演练。

Issue、Wiki、Projects、Actions 和 Packages 通过 Gitea 支持的全局配置及默认仓库配置关闭。仅 `Owners` 能修改仓库设置，团队约定不重新启用这些范围外功能。

## 3. 方案选择

采用 **Gitea + SQLite + 宿主机 Nginx** 的单机方案。

- Gitea：成熟、轻量，覆盖当前所需的 Git 托管和权限能力。
- SQLite：十人以内低并发场景无需单独维护数据库服务，数据可随 Gitea 目录统一备份。
- 宿主机 Nginx：复用现有 HTTPS 和证书续期机制，并反向代理到本机回环端口上的 Gitea。
- 腾讯云 COS：保存每日异地备份，使用对象版本控制提供短期回退能力。

未选择 Forgejo + PostgreSQL，因为当前规模不需要额外数据库服务。未选择 GitLab CE，因为其资源占用、组件数量和运维复杂度明显高于本项目需求。

## 4. 系统架构

```text
浏览器 / Git HTTPS ──> Nginx :443 ──> Gitea Web 127.0.0.1:3000
Git SSH ─────────────────────────────> Gitea SSH :2222
                                           │
                                           v
                                  Gitea 持久化目录
                             仓库 / SQLite / 配置 / 密钥
                                           │
                                      每日一致性备份
                                           │
                                           v
                             腾讯云 COS（版本保留 7 天）
```

### 4.1 组件职责

| 组件 | 职责 | 依赖 |
| --- | --- | --- |
| 宿主机 Nginx | HTTPS、TLS 证书续期、反向代理 | 公网 DNS、80/443 端口 |
| Gitea | 用户、组织、仓库、权限和 Git 协议 | 持久化目录 |
| SQLite | 保存 Gitea 元数据 | Gitea 进程、可靠本地磁盘 |
| 备份任务 | 生成一致性归档、校验并上传 | Gitea、COS 凭证、临时磁盘空间 |
| 腾讯云 COS | 保存当前备份和短期历史版本 | 私有存储桶、版本控制、生命周期规则 |
| 状态检查 | 检查服务、证书、磁盘和备份结果 | systemd 状态与 journal |

组件边界保持简单：Nginx 不保存业务数据，Gitea 的业务数据全部进入持久化目录，备份任务只读取本机数据并写入 COS。

## 5. 部署设计

### 5.1 服务器

- 规格：2 vCPU、2 GB RAM、40 GB SSD 起步。
- 系统：Ubuntu Server 24.04 LTS。
- 容器：基础栈运行 Gitea，后续管理壳设计增加 Workbench；Nginx 与备份任务均由宿主机管理。
- 域名：使用独立代码托管子域名，例如 `git.example.com`。
- 端口：公网开放 80、443 和 Gitea SSH 端口 2222。主机管理 SSH 仅允许密钥登录并限制来源 IP。

镜像必须固定到明确版本号，不能使用 `latest`。普通版本按月评估升级，安全更新及时处理；升级前先完成一次有效备份。

### 5.2 数据持久化

Gitea 仓库、SQLite 数据库、配置、附件和 SSH 相关数据统一挂载到宿主机持久化目录。删除或重建容器不得删除该目录。

敏感配置不进入 Git。管理员初始密码仅在首次创建账号时注入，创建成功后删除；COS 凭证保存在宿主机 `/etc/gitea-stack/cos.env`，属主为 `root`、权限为 `0600`；Gitea 内部密钥随受保护的持久化配置保存。

## 6. 用户与权限

- 关闭公开注册，由管理员创建或邀请账号。
- 使用一个组织，建立 `Owners` 与 `Developers` 两个团队。
- 至少设置两名 `Owners`，避免唯一管理员账号不可用。
- 新仓库默认私有，只由 `Owners` 创建和删除。
- `Developers` 可以浏览、clone、pull、push、创建分支和标签。
- `main` 分支禁止强制推送和删除，但允许有写权限的成员正常直接推送。
- 不要求合并请求，不设置审批人数，也不建立复杂审核规则。
- 管理员必须启用双因素认证，普通成员建议启用；所有 Git SSH 访问使用个人公钥。

## 7. 请求与数据流

### 7.1 Web 与 HTTPS Git

1. 用户访问代码托管域名。
2. 宿主机 Nginx 终止 TLS，并将请求转发给 Gitea 的回环端口。
3. Gitea 完成身份验证和仓库权限判断。
4. Gitea 从持久化目录读取或写入仓库及 SQLite 数据。

### 7.2 SSH Git

1. 用户连接域名的 2222 端口。
2. Gitea 根据用户上传的 SSH 公钥识别身份。
3. Gitea 校验仓库权限后执行 clone、pull 或 push。
4. SSH 通道不经过 Nginx，不提供宿主机 Shell 权限。

## 8. COS 备份

### 8.1 保存策略

- 每天在低使用时段执行一次一致性备份。
- COS 私有存储桶中使用固定对象键保存一个当前日备份；上传期间使用临时对象键，校验成功后才替换当前对象。
- 开启 COS 对象版本控制；覆盖后的非当前版本保留 7 天，再由生命周期规则自动删除。
- COS 临时对象前缀设置 1 天过期规则，清理由中断上传产生的残留对象。
- COS 访问凭证遵循最小权限，只允许指定存储桶和对象前缀所需的上传、查询与恢复操作。
- 使用 COS 服务端加密，存储桶和备份对象不允许公共访问。

### 8.2 执行流程

1. 检查本地剩余空间和 COS 凭证。
2. 停止 Gitea 容器，归档完整持久化目录和部署恢复所需配置，再立即启动 Gitea；预计短暂停机不超过 5 分钟。
3. 计算归档校验值并记录归档大小、完成时间和 Gitea 版本。
4. 将归档上传到带本次时间戳的 COS 临时对象键。
5. 读取临时对象元数据并核对大小与校验信息。
6. 校验成功后，在 COS 内将临时对象复制到固定的当前对象键，确认复制结果，再删除临时对象和本地归档。
7. 任一步骤失败时删除不完整的临时对象、保留原有当前对象，返回非零状态并写入 journal。

同一时间只允许一个备份任务运行。脚本必须注册清理处理，保证归档成功或失败后都会尝试重新启动 Gitea；若 Gitea 未能恢复运行，应将最高优先级错误写入 journal。任何一步失败都应返回非零状态并记录可定位的错误信息。

## 9. 故障处理与恢复

- Gitea 无响应：重启容器；若仍失败，检查日志、磁盘和持久化目录权限。
- 磁盘使用率达到 80%：检查任务返回失败并停止产生新的本地备份临时文件，避免 SQLite 和 Git 写入失败。
- 证书续期失败：管理员检查宿主机 Nginx、现有证书续期任务、DNS、80/443 端口和证书颁发机构连通性。
- 备份失败：不得把失败归档覆盖到 COS 当前对象；任务返回失败并保留错误日志。
- 升级失败：回退到上一固定镜像版本；若发生数据格式不兼容，按升级前备份恢复。
- 主机不可恢复：创建同规格新服务器，安装 Docker 与 Nginx，恢复 Gitea 持久化数据，重新配置 HTTPS 站点并更新 DNS。

恢复目标为 RPO 24 小时、RTO 2 小时。恢复流程写入运维文档，不安排周期性恢复演练。

## 10. 状态检查与日志

采用轻量检查，不引入 Prometheus 等额外平台：

- 定时访问 Gitea 健康检查接口和 HTTPS 首页。
- 检查 TLS 证书剩余有效期。
- 检查磁盘使用率，80% 时返回失败。
- 检查最近一次成功备份时间、归档校验值和 COS 当前对象状态。
- 不发送外部通知；失败检查返回非零状态，systemd 记录失败状态和 journal 日志，由管理员通过宝塔或 systemd 命令查看。

## 11. 验收标准

1. 管理员能创建成员和私有仓库，未授权用户无法查看或 clone 私有仓库。
2. 成员能通过 HTTPS 和 SSH 完成 clone、pull、正常 push、分支与标签操作。
3. `main` 分支的强制推送和删除被拒绝，普通直接推送不要求审批。
4. 容器重建后，用户、仓库、权限和 SSH 密钥保持不变。
5. 域名通过有效 HTTPS 证书访问，HTTP 自动跳转到 HTTPS。
6. 每日备份能生成、校验并上传到私有 COS 存储桶，当前对象可下载且校验一致。
7. 第二次备份覆盖当前对象后，COS 中产生非当前版本；7 天生命周期规则已启用。
8. 使用无效 COS 凭证执行备份会失败、记录明确错误，且不会损坏现有当前备份。
9. 服务异常、磁盘达到阈值或备份超过 24 小时未成功时，健康检查返回失败并记录原因。
